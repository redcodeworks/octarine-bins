# CLAUDE.md

Guidance for Claude Code in this repository. Read it first; the repo's agent (`bins-project` in the hub) is the only writer here.

## What this repo is

**One sentence: this repo builds, signs and promotes ONE image, `ghcr.io/redcodeworks/octarine-bins` (every build-time BINARY dependency of octarine-os: the sched_ext schedulers `scx`, `extest` and Ghostty with its Zig toolchain): built and signed (this repo's key) on `testing`, promoted to `latest` by retag on `main`, and octarine-os pins ONE digest of it (`BINS_*` in its Containerfile).** The octarine-os image build reads the `latest` of that image (resolved to a digest and verified) and never looks at this repo's source tree, tags or workflow results. The code was moved here on 2026-11-16 from `binaries/` in octarine-os (now `src/`), together with its CI. The repo keeps the name octarine-bins (a rename is a later, separate decision).

**The package lists are not here.** Until 2026-11-18 this repo also built `octarine-bins-dx` and `octarine-bins-gx` and carried the build package lists and their installer; the lists now live in octarine-os (build-time lists of its image variants) and octarine-images (the distrobox images), and the two extra images and `/packages` are retired. The GHCR packages `octarine-bins-dx`, `-gx` and their caches are no longer read or written.

`README.md` is user-facing (what, why, how to use, license, credits, disclaimer); implementation details live here.

## Layout of the repo

- `src/` is the image (the name stays because octarine-os pins its digest): `Containerfile`, `components.tsv`, `builder.env`, `lib/` (shared helpers), one directory per component. Build context is `src/`; the pinned builder `src/builder.env` is read by `just build`.
- `src/Containerfile`: ONE multi-stage build. A stage per component (`scx`, `extest`, `ghostty`), an `assemble` stage, a final `FROM scratch`. Build context is `src/`. Every component is required: a failing stage fails the build and nothing is pushed (atomic).
- `src/components.tsv` (component names, one per line, comments allowed), `src/builder.env` (the digest-pinned Fedora builder every stage starts from, passed as `--build-arg BUILDER`), `src/<component>/` (`upstream.env` pin, `build.sh`, for scx `schedulers.tsv`, for ghostty `zig.env` and `fetch-zig.sh`), `src/lib/` (`upstream-env.sh` parser, `fetch-source.sh`, `stage.sh`, `assemble.sh`).
- `.github/workflows/`: `test.yml`, `binaries.yml` (ONE workflow of plain jobs `build`, `sign` and `promote`; no matrix: one image), `bump-pins.yml`, `require-testing-branch.yml`, `promotable.yml` (see "Promotion guard"). `.github/actions/`: `build-image`, `sign-image`, `promote-image` (the steps the jobs run, ONE copy; composite actions, not a reusable workflow, see below) and `setup-tool` (installs pinned cosign or just). `.github/scripts/`: the helpers (below). `.github/dependabot.yml` bumps the pinned actions (PRs into `testing`).
- `Justfile`: `check` (format check), `build <image> <version> <revision> <dir>`, `layout <image> <dir>`, `test [group]` (`dir` is `src`); CI calls `build` and `layout` too. `tests/`: grouped by area, one directory per group and the directory tree is the only list (`tests/pipeline/` CI scripts and the bump flow, `tests/registry/` registry, signing and promotion, `tests/image/` layout and stamp; `tests/conftest.py` and `tests/fakes/` are shared and stay at the top; a test file outside a group, or an empty group, fails `plan_tests.py`). pytest (`just test [group]` runs `uv run --frozen pytest tests/<group>`, nothing installed globally; the fake `skopeo` and `cosign` programs are real executable Python files in `tests/fakes/`, and `tests/fakes/github_api.py` is a fake GitHub API server (it answers with captured real answers from `tests/fakes/api/*.json`, because githubkit validates every field of a typed response; tests adjust a few fields) (stdlib `http.server` in a thread, started by the `github` fixture in `conftest.py`, reached through `GITHUB_API_URL`) (one docstring each says what it fakes; `tests/conftest.py` puts the directory on PATH, no network; `tests/fakes/bump_run.py` and `bump_checks.py` are the stubs the weekly test copies next to the real `bump_weekly.py`), so no test builds code from strings): `test_retry.py` (the decorator), `test_github.py` (the SDK against the fake API: a 404 raises after one request, a dropped connection is retried), `test_sanity.py`, `test_registry.py`, `test_skip_promote.py` (real git repositories), `test_layout.py` (the real assembler into the layout checker), `test_pins.py` (the real Ghostty writer into the real reader; the weekly decisions with a table of API answers), `test_bump_weekly.py` (real git, stub `gh`).
- `cosign.pub` (public, committed) is this repo's OWN key, not shared with octarine-os (one key per repo: a shared key would let a compromised workflow here sign octarine-os images). octarine-os verifies `octarine-bins` with its own copy of this public key; when the key changes, that copy changes first or together. `cosign.key` sits in the repo directory, git-ignored: NEVER read, print, copy, stage or commit it. CI signs with the secret `SIGNING_SECRET` of the environment `signing` (branch policy `main`, `testing`); do not create other secrets or tokens.

## The image layout (the contract with octarine-os)

```
/binaries/            (the image root; octarine-os bind-mounts the image at /binaries)
  COMPONENTS          component names, one per line (written by src/lib/assemble.sh from components.tsv)
  SOURCE, BUILDINFO   the components' records one after the other, each under a [name] heading
  LICENSES/           union of the component license directories
  scx/       bin/<scheduler>..., schedulers.tsv (tab separated, 4 fields: name, bin/name, minimum kernel, description), SOURCE, BUILDINFO, LICENSES/
  extest/    lib/libextest.so (32-bit), lib64/libextest.so, SOURCE, BUILDINFO, LICENSES/
  ghostty/   root/usr/... (the installed tree), FILES (one path under root/ per line), SOURCE, BUILDINFO, LICENSES/
```

**No `packages/`, no installer:** the image root holds only `/binaries`'s files above. octarine-os's `install-binaries.sh` still tolerates a top-level `packages/` directory (it is not a component), so images that carried one are still readable; this image has none since 2026-11-18. Package lists and their installers live in octarine-os and octarine-images, not here.

**Build on content, stamp every build (2026-11-17).** A push to `testing` builds the image only if its CONTENT changed since the commit its `testing` image was built from. Every build is stamped with `org.opencontainers.image.version` (`<UTC date>-<short sha>`), `.revision` (the full commit it was built from) and `.created` (`just build <image> <version> <revision> <dir>` runs the build and then `stamp_image.py`: a separate `podman build --no-cache` of a three-line Containerfile on top of the built image, so the stamp can NEVER be served from the layer cache; before 2026-11-17 the labels were `LABEL` lines fed by `ARG`s in the final stage, and a cached build kept the old labels: an input changed without changing the image bytes left `testing` labeled with an older commit, promotion refused and every later push rebuilt; `built=` in `SOURCE` is the component's build time and stays with its cached layer), so the `revision` label always names the commit of the latest build. Skip: the content inputs at the revision label's commit equal those at `HEAD` and `testing` verifies with `cosign.pub`. Promote: retag the tested, signed `testing` digest to `latest` after checking that its revision's content equals `main`'s content. So a new digest always means a build ran for a content change (a build that is not skipped is never byte-identical: the stamp's `created` carries the time; the layers are those of the content, only the config and so the manifest digest differ), and octarine-os's weekly bump PR follows content changes only. Content is defined ONCE, `ci.inputs(<dir>)` in `.github/scripts/ci.py`, a hand-written list that the `sanity` copy guard checks against each Containerfile's `COPY` lines, used by the skip AND the promotion guard (`ci.content_id`: sha256 of `git ls-tree -r <commit> -- <inputs>`, every path under an input counts, a `.md` file included): all of `src/` (Containerfile, `components.tsv`, `builder.env`, `lib/`, the components). Not content: the Justfile, `.github/**` (workflows, actions, scripts), tests, READMEs and other docs (because they are not inputs, not because of a filter). **Tooling-only changes build NOTHING**; they are validated by a manual dispatch (`gh workflow run binaries.yml --ref testing`, which always builds) or by the next content change. Because the stamp varies, never compare digests of two builds of the same content: they differ by design. The registry tags are `<UTC date>-<short sha>` (immutable: `push_image.py` keeps an existing tag and its digest instead of overwriting it, which only happens when the same commit is built twice on one day), `testing` and `latest`; the older `inputs-<hash>` tags in the registry (from #29, 2026-11-17) are unused.

**A layout change goes reader-first:** octarine-os (`build_files/install-binaries.sh`, `gen-schedulers.sh`, the smoke tests) first accepts BOTH the old and the new layout, then this repo writes the new one, then the OS drops the old one. Say so under `Needs from hub:` whenever the layout would change. `.github/scripts/binaries_layout.py` (run on every built image by `just layout`) is this repo's copy of what the reader needs; `tests/image/test_layout.py` runs the real assembler into it.

## Branches, CI and promotion (GitLab Flow)

1. A push to a feature branch (`feat/`, `fix/`, `chore/`) runs `test.yml`: job `plan-tests` (lists the groups), job `sanity` (`sanity.py`: `bash -n` on every shell script, a compile of every Python file, workflow parse; then `just check`), one job `tests (<group>)` per group (`just test <group>`), job `test` (the aggregate, `if: always()`, succeeds only when all of those did; the one required name, which `bump_checks.py` reads from the dispatched run) and job `secrets` (gitleaks over the full history). The same workflow has job `zizmor` (workflow audit with the pinned zizmor, `.github/zizmor.yml` config; runs on every push and weekly on Wednesdays 06:00 UTC, which is the only job of the scheduled run; skipped on a dispatch; not required, `test` does not depend on it). Open a PR into `testing`. Required checks (ruleset, set by the hub): `test` and `secrets`.
2. A push to `testing` runs `binaries.yml`: one run, concurrency group per ref, plain jobs (no matrix: one image). `build` (`.github/actions/build-image`: first `binaries_skip.py`, see "Skipping a build"; then `just build`: the whole multi-stage build with a registry layer cache (below); `just layout`; `push_image.py` pushes the immutable tag `<date>-<sha>` and prints the digest) hands image, version, skipped and digest to `sign` as job outputs. `sign` (`environment: signing`, `.github/actions/sign-image`) runs `cosign sign` on that digest with the old bundle format, verifies with `cosign.pub`, and only THEN `skopeo copy --preserve-digests` to `:testing`, reads it back with `registry.settled`, verifies again. So `testing` never points at an unsigned image. `sign` runs only on `testing` (the `signing` environment admits only `main` and `testing`; a branch dispatch gets no sign job) with `needs: build`: when `build` fails, `sign` is skipped and the run is red. A push that skipped on unchanged content succeeds with the signing steps skipped. Why one workflow with composite actions rather than a reusable workflow (as octarine-os's dx image does): the job names are required checks (`Build the binaries image`, `Sign the binaries image and move testing`, `Promote the tested binaries image`, `Promotable: octarine-bins`), and a job of a reusable workflow is reported as `<caller job> / <called job>`; the signing environment secret also does not reach a job inside a reusable workflow (observed 2026-11-16). Composite actions run inside the workflow's own job, so the names and `environment: signing` stay and the steps exist once.
3. A promotion PR from `testing` into `main` (only from `testing`: `require-testing-branch.yml`; Kevin merges it) makes the push to `main` run the `promote` job (`.github/actions/promote-image`): `binaries_promote.py` retags the TESTED, signed `:testing` digest to `:latest` (no rebuild). It fails loudly, changing nothing, unless `testing` exists, verifies with `cosign.pub` and IS the build of these inputs (guard below); when `latest` already is that digest it does nothing; afterwards it reads the tag back and verifies through `:latest`. Nothing else moves `latest`.
4. A dispatch from any other ref builds for validation and publishes nothing. By hand: `gh workflow run binaries.yml --ref testing` rebuilds, `--ref main` promotes (promotion is idempotent).
5. Builds are not path filtered: every push to `testing` and `main` runs the workflow (`main` only promotes). Runs of one ref queue, none is cancelled (`cancel-in-progress: false`), so two runs never move `testing` out of order. A superseded older `testing` run may be cancelled by hand; never a `main` or a signing run, never the tip.

Cost of an unchanged push to `testing` (skip path): 1 workflow run, 2 jobs (`build` and `sign`), roughly 30 to 60 s for `build` (checkout, login, cosign install, the registry reads) and a few seconds for `sign`; on `main` one `promote` run of about a minute that finds `latest` already the tested digest.

Promotion guard: `binaries_promote.py <image> <dir>` also fails, changing nothing, unless `testing` IS the build of exactly what is promoted: the content (`ci.content_id`, above) at the commit of `testing`'s `revision` label must equal the content of `HEAD` of the main checkout (the promotion PR's merge commit; its content equals the testing tip's when main has nothing testing lacks, which the ruleset ensures; the first promotion works the same). Tooling and docs are no content, so they never make the image stale. A mismatch means the build on testing is running, failed, or testing moved on. A cosign read error is printed as such, not as 'not signed'. Hand fix: wait for the tip's build on `testing` to be green, then `gh run rerun` the promote run (or `gh workflow run <caller>.yml --ref main`).

**The promotion PR checks that its promotion would succeed (2026-11-17).** `promotable.yml` runs on `pull_request` into `main` (opened, synchronize, reopened): one job, `Promotable: octarine-bins`, `binaries_promote.py --check <image> <dir>` on the PR's merge result (what `main` will contain), with registry read and cosign, no signing key. `--check` is the same function as the real promote (`acceptable()`: testing exists, verifies with `cosign.pub`, its revision label's content equals the checkout's), minus the retag, so a promote that would refuse is red BEFORE the merge. Timing: the promotion PR is usually opened while the build on `testing` still runs, so the check can be red with 'testing moved on' (or 'could not be read'); that is correct, not a fault: when the build and sign jobs are green, re-run the failed `Promotable` jobs (`gh run rerun <id> --failed`, or the UI) or push again. A tooling-only change builds nothing and keeps the old label, whose content equals main's, so it is green at once. The name is a required context of the `main` ruleset (added by the hub after they ran once).

## Speed: parallel stages, layer cache, skipped builds (2026-11-16)

- **Parallel stages:** `just build` passes `--jobs 3`, so the scx, extest and ghostty stages build at the same time (they share nothing but the builder). The runner has about 4 cores, so only part of the gain shows.
- **Layer cache (2026-11-17):** `--layers --cache-from ghcr.io/redcodeworks/octarine-bins-cache` on every build, plus `--cache-to` the same package only on `testing` (`main` builds nothing). buildah keeps its layers as tags of ONE repository, so a cache needs its own package. The cache is a separate package, never the image's tags; it needs `packages: write` (the build job has it; GITHUB_TOKEN, nothing else). Invalidation: a new `builder.env` digest changes the `FROM` of every stage, so everything rebuilds; a Ghostty pin change rebuilds only the ghostty stage (the earlier layers, dnf included, hit); an scx pin only scx; a change to `src/lib` rebuilds all stages (`COPY lib`); a change to a stage's `COPY` directory rebuilds that stage from the `COPY` on. The dnf layers are frozen until the builder pin or the text of the instruction changes: Fedora package updates reach the binaries only with a builder bump or an edit of that line (a reproducibility gain, accepted). The first run, or a package that does not exist yet, is a cold build, not a failure. The cache only saves time: what is published is decided by the layout check before the push and by the signature. If the cache cannot be read for another reason and podman fails, the build fails plainly: re-run it, or run the workflow once with the cache flags removed.
- **Skipping a build** (`binaries_skip.py`, push to `testing` only; a dispatch always builds): when the content of this commit equals the content at the `revision` label's commit of `testing` and that image verifies with `cosign.pub` ("Build on content"), the `build` step is skipped and the `sign` job does nothing. Both jobs still run and succeed (the ruleset requires their names `Build the binaries image` and `Sign the binaries image and move testing`; never use `paths:` filters). So a change to anything under `src/` rebuilds the image; the Justfile, workflows, actions, scripts, tests and READMEs rebuild nothing. No testing image, a testing image without a valid revision label, an unfetchable revision, other content, or an image that does not verify (for example signed with an old key) means build. **Copy guard:** `sanity.py` (the `sanity` step of `test`) reads every `*/Containerfile` and fails when a COPY/ADD source from the build context, or from a `--from=<name>` that is a `--build-context` of the Justfile (the guard reads the name-to-path pairs from there), is not inside the `ci.inputs` of that image (stage names are not repo paths; a variable or URL source and `RUN --mount=type=bind` fail as unchecked; a new image directory without `ci.inputs` fails). So a new COPY needs its path added to `ci.inputs` in the same change. The Justfile itself is deliberately not an input: its build flags (`--jobs`, `--build-context` pairs, the stamp step) do not change the content that lands in an image, and counting it would rebuild the image on every recipe edit; a `--build-context` change that matters shows up as a changed or missing COPY source, which the guard catches. A registry or cosign READ error fails the run instead of guessing. The first run builds (no testing image). A rebuild by hand: `gh workflow run binaries.yml --ref testing`.

## Pin policy

Pins: scx and extest (`src/<c>/upstream.env`: tag and/or commit), Ghostty (`src/ghostty/upstream.env`) with Zig (`src/ghostty/zig.env`: Zig changes ONLY together with a Ghostty pin, its minor follows from the tag), the Fedora builder digest (`src/builder.env`, bumped once the digest has been the tag's value for 7 days), the GitHub Actions (by commit, Dependabot), the CI tool versions (cosign, just, gitleaks, zizmor: by hand). Pins change only through a PR Kevin approves. `bump-pins.yml` (Monday 07:00 UTC, or `gh workflow run bump-pins.yml --ref testing`; `-f dry_run=true` lists what it would open, keep or close and creates nothing) opens ONE PR PER PIN into `testing`, each independent: branch `bump/scx-YYYYMMDD`, `bump/extest-...`, `bump/ghostty-...` (Ghostty and Zig together, Zig never alone) or `bump/builder-...`, or `bump/python-deps-...` (`uv lock --upgrade`: newer locked versions of the CI scripts' own dependencies, only `uv.lock` changes; the `pyproject.toml` ranges and the Python version stay), cut from current `testing`, one commit, only that pin's lines (different files, so no conflicts): merge any subset in any order, close the rest. At most one open PR per pin (found by the head prefix `bump/<pin>-`), and no force-push is ever used: an open PR that already proposes the same `to` value stays (reruns are idempotent); an open PR with an older value is REPLACED (a new branch `bump/<pin>-YYYYMMDD`, `-2`, `-3` if the name exists, and a new PR are made first, then the old PR is closed with a comment pointing at the new one and its branch deleted); an open PR whose value `testing` already has is closed as stale with a comment; nothing moved means no branch and no PR. Same semantics as octarine-os's bump. A pin whose upstream cannot be read leaves its open PR alone and turns the run red. It uses only `GITHUB_TOKEN` (no PATs, no cross-repo PRs). Needs the repository setting "Allow GitHub Actions to create and approve pull requests". PRs opened with `GITHUB_TOKEN` start no workflow, so `bump_checks.py` dispatches `test.yml` on `testing` with `ref=<bump commit>` (its run is named `Test of <sha>`, so parallel PRs do not collide; each pin's job waits for its own, hence the 30-minute job timeout) and posts check runs named `test` and `secrets` on the bump commit with the real results (`actions: write`, `checks: write`). The workflow is a MATRIX, one job per pin (`Bump <pin>`, `fail-fast: false`; the matrix in `bump-pins.yml` is the only list of pins and passes its pin to `bump_weekly.py` as `BUMP_PINS`, which is required, so a hand run names the pins: `BUMP_PINS=scx python -I .github/scripts/bump_weekly.py`); adding a kind adds one matrix entry. The jobs do not collide: branches are per pin, test runs and check runs are keyed by the bump commit, and `python-deps` (`uv.lock`) and `python` (`.python-version`) touch different files. Each job checks out `testing` and sets up uv and Python itself (cache on; no signing key there), and one failing pin turns only its own job red. Scheduled workflows run only from the default branch, so the schedule starts after the first promotion.

## What octarine-os expects

`octarine-bins:latest` exists, verifies with this repo's `cosign.pub` (the OS build resolves the tag to a digest once and verifies it), and has the layout above, with exactly the components its installer's `required` list names (`scx extest ghostty`), no more. A new or removed component means a coordinated change on both sides (reader first).

**Adding a component:** a stage copied from `src/Containerfile`, its pin and build script in `src/<name>/`, its name in `src/components.tsv`, a case in `binaries_layout.py`, and a pin kind for the weekly bump (`bump_run.py`, the kind list of `bump_weekly.py`, the tests). The OS reader learns the component first. The scheduler list is `src/scx/schedulers.tsv`; octarine-os generates its registry from the copy inside the image.

## Failure modes and hand fixes

- A component does not build (an upstream download failed, a Fedora package moved, Ghostty/Zig broke): `build` is red, nothing is pushed, `testing` and `latest` stay. Re-run the run if it looks transient; otherwise pin back the component (`upstream.env`; for Ghostty also `zig.env`, together) in a PR. A component that keeps failing is removed in a coordinated change (reader first): its stage, directory, line in `components.tsv`, the layout case in `binaries_layout.py`, and the OS side.
- `sign` fails after a push (the job `Sign the binaries image and move testing`): the `<date>-<sha>` tag exists unsigned, `testing` did not move. Re-run `sign`, or push to `testing` again. An unsigned `<date>-<sha>` tag is never promoted (only `testing` and `latest` are).
- Promotion fails ("not signed", "does not exist", "could not be read"): fix the testing build, then re-run the failed promote jobs (`gh run rerun --failed`, or `gh workflow run binaries.yml --ref main`). Exit 4 from a registry or cosign read means a read error, never "absent".
- Never attach anything to an image digest in the registry (an OCI referrer such as an attestation pushed with `push-to-registry`): cosign v3 then fails `cosign verify --key cosign.pub` on that digest ("no matching attestations: expected key signature, not certificate"). Only the `--new-bundle-format=false` flag verifies it; replace such a digest by rebuilding (found 2026-11-17, attestations #46 reverted).
- The first push of a new package creates it private in GHCR (a new image): Kevin makes each public and links it to the repo (package settings, "Manage Actions access" with Write for this repository) by hand. The rulesets list the required contexts (the job names above); the hub changes them.
- Old testing images accumulate; deleting versions is Kevin's, by hand in the packages UI.

## Scripts (`.github/scripts`)

**Python for the CI side** (the Containerfile and component build steps stay bash). Dependencies are declared in `pyproject.toml` (`githubkit`, which brings `httpx` and `pydantic`; `packaging`; `pyyaml`; `pytest` in the `dev` group) and pinned with hashes in the committed `uv.lock`; the Python itself is pinned EXACTLY by `.python-version` (`3.14.10`, a uv-managed interpreter; `requires-python >=3.14` is only the floor the lock is valid for). The runner image's system Python is NOT used: the composite action sets `UV_PYTHON_PREFERENCE=only-managed`, so uv downloads the pinned interpreter instead of silently taking `/usr/bin/python3.14`, whose patch version floats with the runner image; uv checks the sha256 embedded in its own pinned release metadata after the download. The weekly bump has a `python` kind that proposes the newest patch release of that minor which the pinned uv can install (a newer one appears after a uv bump, which is by hand). Every script runs as `uv run --frozen --no-dev python -I .github/scripts/<name>.py`: `--frozen` means nothing is resolved at run time (the lock decides), and `uv run` creates the venv and installs it, so no separate sync step is needed. `-I` keeps the script's directory off `sys.path`, so each script starts with two lines that add it back. In CI the composite action `.github/actions/setup-ci-python` installs uv (`astral-sh/setup-uv`, SHA-pinned) with its cache ON, keyed on `uv.lock` and `.python-version`, and `cache-python`, so the managed Python is saved on the first run and restored later (a Python or lock bump changes the key and invalidates it). The sign job holds the signing key and restores no cache of any kind (`cache: false` on both setup actions): it installs the uv packages from the frozen lock, downloads the pinned managed Python and installs cosign fresh on every run, and those install steps verify what they download (uv checks the sha256 of its managed Python; the pinned `sigstore/cosign-installer` verifies cosign against a checksum embedded in the action). The standard library is used for `argparse` (every script that reads arguments, `--help` shows the first sentence of its docstring), `logging` (`ci.log`, one handler that writes the `::error::` and `::warning::` annotations; no scattered prints) and `subprocess` (argument lists, never a shell); `packaging.version.Version` orders versions; `pydantic` validates what untrusted JSON is read into (`pins.Pin` and `pins.Decision` dataclasses, the Zig index and the release JSON as models); `httpx` downloads what is not the GitHub API (the Zig index, with a timeout and `follow_redirects`). One sentence at the top of each file says what it does. **Shared code lives in `ci.py`** (THE helpers file: `log`, `@retry`, `github()`, `retry_decision`, `git`, `group`, `version`, `emit`, `inputs(dir)`, `arg_parser`) **and `registry.py`** (every skopeo, cosign and podman call). **The rules: the GitHub API is used through the githubkit SDK directly (`gh = ci.github()`, then `gh.rest.<group>.<operation>(...)`, typed responses, `gh.rest.paginate(...)` as a lazy iterator; keep the `gh` variable, `gh.rest` only holds a weak reference to it); its `auto_retry` handles rate limits and 5xx, `ci.retry_decision` adds transport errors through the SDK's own retry-decision API, and its exceptions are not wrapped: an error ends the script with the SDK's traceback, and `RequestFailed` is caught only where a decision depends on the status (a 404 means "no release", or "the fork does not have the commit"). Every external command and every other network call goes through `@ci.retry`; nowhere else is there a retry loop.** `@retry(on=(...), attempts=, delay=, backoff=)` retries only the exception types in `on` (transient failures), waits `delay` x try number seconds (RETRY_TRIES 3 and RETRY_DELAY 5 by default, shortened through the environment in tests), never retries any other exception, and re-raises the last error with ` (failed N attempts)` in its message. A definitive answer is a typed exception that is NOT in `on`, so it surfaces at once: `registry.Absent` (skopeo: the tag does not exist), `registry.NotVerified` (cosign: no valid signature), a githubkit `RequestFailed` (an error status); `registry.ReadError`, `ci.NetworkError` and `ci.ServerError` are the transient ones. So "could not read" is never taken for "not there". The API server comes from `GITHUB_API_URL` and the token from `GITHUB_TOKEN` (workflows that use the API set it from `github.token`), so the tests can point the scripts at a local fake. Scripts (each has a `main`): `push_image.py`, `stamp_image.py` (the version, revision and created labels, a no-cache layer-less step after `just build`), `sign_image.py` (sign, verify, copy to `testing`, read back, verify), `binaries_skip.py`, `binaries_promote.py`, `binaries_layout.py <image> <dir>` (exports the image with podman and checks it; `check()` is what the tests call), `upstream_check.py` and `ghostty_check.py` (the decisions; each also has `check()`, which `bump_run.py` calls), `bump_run.py` (one pin), `bump_weekly.py` (all pins), `bump_checks.py` (its sleep is a poll for the dispatched run to appear, not a retry), `sanity.py`; `pins.py` holds the pin files (the Python twin of `src/lib/upstream-env.sh`, which the build scripts inside the container still use). **The original shell scripts and tests are kept in `.archive/shell-ci/`** (see its README: a revert is a file move); nothing runs or checks them and they are not an image input.

**Style of the Python scripts** (Kevin, 2026-11-18): prefer expressions over statements: compute a value with a comprehension, generator expression, conditional expression, `any`/`all`/`sum`/`min`/`max`/`sorted(key=)`, `itertools` or a function that returns it, and bind it once, instead of mutating an accumulator or a flag. The exception is `match`: it branches on a value or shape (decision tables, classification, exit-code dispatch) with each arm returning its value. When the per-item work is messy (match, try/except, logging, subprocess), it goes into a small named helper that takes one item and returns its value, and the caller is a flat comprehension (`results = [check(x) for x in xs]`); inlined nested conditionals, deep nesting and walrus puzzles are discouraged, and a helper that only has side effects runs in a plain loop, never a throwaway comprehension. Logging: a script's RESULT (what a workflow or a caller captures: a decision line, `key=value`, a digest) goes to stdout through `ci.result` / `ci.emit` and nothing else does; every reason, progress line and diagnostic is `ci.log.info` / `warning` / `error`, and the handler writes all of them to stderr, so `x=$(script.py)` captures the result alone (`test_stdout_holds_only_the_result`). WARN vs ERROR: a check that breaks nothing is `log.warning` (a `::warning::` annotation, the step stays green); `log.error` with a nonzero exit only for what makes the result wrong or unsafe (signature, digest, promotion, a published tag). Formatting: ruff (Python) and shfmt (shell, every tracked shell file except the frozen `.archive/shell-ci/`) run with their defaults, no configuration files and no lint rules; the opt-in pre-commit hook (`just hooks`, `githooks/pre-commit`) formats the staged files and re-stages them (it skips shfmt with a message when that is not installed); CI has no format check.
