# CLAUDE.md

Guidance for Claude Code in this repository. Read it first; the repo's agent (`bins-project` in the hub) is the only writer here.

## What this repo is

**One sentence: octarine-bins builds three independent images (`octarine-bins` for every octarine-os variant, `octarine-bins-dx`, `octarine-bins-gx`), each built and signed on `testing`, promoted to its own `latest` by retag on `main`, and consumed by the OS image pinned by digest.** The base image holds the binaries every variant installs (the sched_ext schedulers `scx`, `extest`, Ghostty with its Zig toolchain), `ghcr.io/redcodeworks/octarine-bins`. `-dx` and `-gx` (added 2026-11-16) are for binaries only the dx or the gx image needs; both are EMPTY skeletons for now (no component, see "The empty image"). The octarine-os image build reads the `latest` of the images it uses (resolved to a digest and verified) and never looks at this repo's source tree, tags or workflow results. The code was moved here on 2026-11-16 from `binaries/` in octarine-os (now `src/`), together with its CI.

`README.md` is user-facing (what, why, how to use, license, credits, disclaimer); implementation details live here.

## Layout of the repo

- One directory per image: `src/` (the base image, octarine-bins; the name `src` stays because octarine-os pins its digest), `dx/` and `gx/` (each `Containerfile`, `components.tsv`, a `README.md` on adding a component). Build context of an image is its directory; the SHARED helpers live once, in `src/lib`, and the other images reach them as the named build context `lib` (`just build` passes `--build-context lib=src/lib`; `COPY --from=lib ...`). The pinned builder `src/builder.env` is shared the same way.
- `src/Containerfile`: ONE multi-stage build. A stage per component (`scx`, `extest`, `ghostty`), an `assemble` stage, a final `FROM scratch`. Build context is `src/`. Every component is required: a failing stage fails the build and nothing is pushed (atomic).
- `src/components.tsv` (component names, one per line, comments allowed), `src/builder.env` (the digest-pinned Fedora builder every stage starts from, passed as `--build-arg BUILDER`), `src/<component>/` (`upstream.env` pin, `build.sh`, for scx `schedulers.tsv`, for ghostty `zig.env` and `fetch-zig.sh`), `src/lib/` (`upstream-env.sh` parser, `fetch-source.sh`, `stage.sh`, `assemble.sh`).
- `.github/workflows/`: `test.yml`, `binaries.yml`, `binaries-dx.yml`, `binaries-gx.yml` (the three thin callers: build, sign, promote of one image each), `bump-pins.yml`, `zizmor.yml`, `require-testing-branch.yml`. `.github/actions/`: `build-image`, `sign-image`, `promote-image` (the steps the three callers share, ONE copy; composite actions, not a reusable workflow, see below) and `setup-tool` (installs pinned cosign or just). `.github/scripts/`: the helpers (below). `.github/dependabot.yml` bumps the pinned actions (PRs into `testing`).
- `Justfile`: `check` (format check), `build <image> <version> <revision> <dir>`, `layout <image> <dir>`, `test` (`dir` is `src`, `dx` or `gx`); CI calls `build` and `layout` too. `tests/*.sh`: stub-based tests, no network.
- `cosign.pub` (public, committed) is this repo's OWN key, not shared with octarine-os (one key per repo: a shared key would let a compromised workflow here sign octarine-os images). octarine-os verifies `octarine-bins` with its own copy of this public key; when the key changes, that copy changes first or together. `cosign.key` sits in the repo directory, git-ignored: NEVER read, print, copy, stage or commit it. CI signs with the secret `SIGNING_SECRET` of the environment `signing` (branch policy `main`, `testing`); do not create other secrets or tokens.

## The image layout (the contract with octarine-os)

```
/binaries/            (the image root; octarine-os bind-mounts the image at /binaries)
  COMPONENTS          component names, one per line (written by src/lib/assemble.sh from components.tsv)
  SOURCE, BUILDINFO   the components' records one after the other, each under a [name] heading
  LICENSES/           union of the component license directories
  scx/       bin/<scheduler>..., schedulers.tsv (tab separated, 4 fields: name, bin/name, minimum kernel, description), SOURCE, BUILDINFO, LICENSES/
  extest/    lib/libextest.so (32-bit), lib64/libextest.so, SOURCE, BUILDINFO, LICENSES/
  ghostty/   root/usr/... (the installed tree), FILES (one path under root/ per line), SOURCE, BUILDINFO, LICENSES/
```

**The empty image (`octarine-bins-dx`, `-gx`, until they get a component):** `/COMPONENTS` is EMPTY (zero bytes), there is no `/binaries/<name>/` directory, `BUILDINFO` and `SOURCE` exist and are empty, `LICENSES/` exists and is empty, and the labels are set. Zero components means nothing to install. `src/lib/assemble.sh --allow-empty` writes it (the base never passes the flag: an empty list there is an error), and `binaries-layout.sh --allow-empty` accepts it (`just layout` passes the flag for `dx` and `gx` only; the base must still hold scx, extest and ghostty, and a base missing one fails). The octarine-os reader today treats an empty `COMPONENTS` as "not an assembled binaries image" (`test -s`) and has a fixed `required` list, so the dx/gx reader must accept zero components before the OS installs these images; it is a new reader step in octarine-os, not a layout change of the base.

The label `org.opencontainers.image.version` is `<UTC date>-<short commit sha>` (also the immutable tag of that build); `...revision` is the full commit sha. Informational: the OS does not check either (the old tree-id key is gone, the OS reads `latest` only). Why: a tag per commit is easy to find from a workflow run, and the content identity does not need to be carried because `latest` is the signed digest of one build.

**A layout change goes reader-first:** octarine-os (`build_files/install-binaries.sh`, `gen-schedulers.sh`, the smoke tests) first accepts BOTH the old and the new layout, then this repo writes the new one, then the OS drops the old one. Say so under `Needs from hub:` whenever the layout would change. `.github/scripts/binaries-layout.sh --assembled` (run on every built image by `just layout`) is this repo's copy of what the reader needs; `tests/image-layout.sh` runs the real assembler into it.

## Branches, CI and promotion (GitLab Flow)

1. A push to a feature branch (`feat/`, `fix/`, `chore/`) runs `test.yml`: job `test` (`bash -n` on every script, workflow parse, `just check`, `just test`) and job `secrets` (gitleaks over the full history). `zizmor.yml` audits `.github/` on PRs that touch it. Open a PR into `testing`. Required checks (ruleset, set by the hub): `test` and `secrets`.
2. A push to `testing` runs the three callers `binaries.yml`, `binaries-dx.yml` and `binaries-gx.yml`, each with its own concurrency group, so each image has its own queue. Per image: `build` (`.github/actions/build-image`: first `binaries-skip.sh`, see "Skipping a build"; then `just build`: the whole multi-stage build with a registry layer cache (below); `just layout`; `push-image.sh` pushes the immutable tag `<date>-<sha>` and prints the digest), then `sign` (`environment: signing`, `.github/actions/sign-image`: `cosign sign` that digest with the old bundle format, verify with `cosign.pub`, and only THEN `skopeo copy --preserve-digests` to `:testing`, read it back with `registry-settled.sh`, verify again). So `testing` never points at an unsigned image. Why callers and composite actions rather than one reusable workflow (as octarine-os's dx image does): the job names are required checks (`Build the binaries image`, `Sign the binaries image and move testing`, and the same with `dx ` and `gx `), and a job of a reusable workflow is reported as `<caller job> / <called job>`; the signing environment secret also does not reach a job inside a reusable workflow (observed 2026-11-16). Composite actions run inside the caller's own job, so the names and `environment: signing` stay and the steps exist once.
3. A promotion PR from `testing` into `main` (only from `testing`: `require-testing-branch.yml`; Kevin merges it) makes the push to `main` run each caller's `promote` job (`.github/actions/promote-image`): `binaries-promote.sh` retags the TESTED, signed `:testing` digest of that image to its `:latest` (no rebuild). It fails loudly, changing nothing, unless `testing` exists, verifies with `cosign.pub` and was built from this image's trees (guard below); when `latest` already is that digest it does nothing; afterwards it reads the tag back and verifies through `:latest`. Nothing else moves `latest`.
4. A dispatch from any other ref builds for validation and publishes nothing. By hand, per image: `gh workflow run <caller>.yml --ref testing` rebuilds, `--ref main` promotes.
5. Builds are not path filtered: every push to `testing` and `main` runs all three callers (`main` only promotes). Runs of one ref and image queue, none is cancelled (`cancel-in-progress: false`), so two runs never move `testing` out of order. A superseded older `testing` run may be cancelled by hand; never a `main` or a signing run, never the tip.

Cost of an unchanged push to `testing` (skip path): 3 workflow runs, 6 jobs (`build` and `sign` each), roughly 30 to 60 s per `build` (checkout, login, cosign install, the registry reads) and a few seconds per `sign`, in parallel; on `main` 3 `promote` runs of about a minute that find `latest` already the tested digest.

Promotion guard: `binaries-promote.sh <image> <dir>` also fails, changing nothing, unless the testing image was built from exactly the binaries promoted: the image's trees (`binaries-inputs.sh <dir> --trees`: `src/` for the base; `dx/` or `gx/` plus `src/lib` and `src/builder.env` for the others) at the commit in its `org.opencontainers.image.revision` label must equal those of `HEAD` of the main checkout (the promotion PR's merge commit; they equal the testing tip's when main has nothing testing lacks, which the ruleset ensures; the first promotion works the same). Only those trees are compared, because a push that did not change the build inputs builds nothing and leaves `testing` at an older revision. A mismatch means the build on testing is running, failed, or testing moved on. Hand fix: wait for the tip's build on `testing` to be green, then `gh run rerun` the promote run (or `gh workflow run <caller>.yml --ref main`).

## Speed: parallel stages, layer cache, skipped builds (2026-11-16)

- **Parallel stages:** `just build` passes `--jobs 3`, so the scx, extest and ghostty stages build at the same time (they share nothing but the builder). The runner has about 4 cores, so only part of the gain shows.
- **Layer cache:** `--layers --cache-from ghcr.io/redcodeworks/<image>-cache` on every build, plus `--cache-to` the same package only on `testing` (`main` builds nothing). One cache package per image (`octarine-bins-cache`, `octarine-bins-dx-cache`, `octarine-bins-gx-cache`): buildah keeps its layers as tags of ONE repository, so tags cannot keep three caches apart. The cache is a separate package, never the image's tags; it needs `packages: write` (the build job has it; GITHUB_TOKEN, nothing else). Invalidation: a new `builder.env` digest changes the `FROM` of every stage, so everything rebuilds; a Ghostty pin change rebuilds only the ghostty stage (the earlier layers, dnf included, hit); an scx pin only scx; a change to `src/lib` rebuilds all stages (`COPY lib`); a change to a stage's `COPY` directory rebuilds that stage from the `COPY` on. The dnf layers are frozen until the builder pin or the text of the instruction changes: Fedora package updates reach the binaries only with a builder bump or an edit of that line (a reproducibility gain, accepted). The first run, or a package that does not exist yet, is a cold build, not a failure. The cache only saves time: what is published is decided by the layout check before the push and by the signature. If the cache cannot be read for another reason and podman fails, the build fails plainly: re-run it, or run the workflow once with the cache flags removed.
- **Skipping a build** (`binaries-skip.sh`, push to `testing` only; a dispatch always builds): when the current `testing` image's revision label names a commit whose build inputs equal this commit's, and the image verifies with `cosign.pub`, the `build` step is skipped and the `sign` job does nothing. Both jobs still run and succeed (the ruleset requires their names `Build the binaries image` and `Sign the binaries image and move testing`; never use `paths:` filters). Inputs, the simplest safe rule, listed in ONE place, `.github/scripts/binaries-inputs.sh <dir>`: the image's directory (for `dx` and `gx` also the shared `src/lib` and `src/builder.env`), `Justfile`, the image's caller workflow, `.github/actions/build-image`, `.github/scripts/push-image.sh` and `.github/scripts/binaries-layout.sh` (compared as a hash of `git ls-tree -r`). So a change to `src/lib`, the builder, the Justfile or the shared build files rebuilds all three images, a change to `dx/` only dx; docs, tests, other workflows and scripts do not rebuild. No testing image, no revision label, an unfetchable revision or an image that does not verify (for example signed with an old key) means build. A registry or cosign READ error fails the run instead of guessing. The first run builds (no testing image). A rebuild by hand: `gh workflow run <caller>.yml --ref testing`.

## Pin policy

Pins: scx and extest (`src/<c>/upstream.env`: tag and/or commit), Ghostty (`src/ghostty/upstream.env`) with Zig (`src/ghostty/zig.env`: Zig changes ONLY together with a Ghostty pin, its minor follows from the tag), the Fedora builder digest (`src/builder.env`, bumped once the digest has been the tag's value for 7 days), the GitHub Actions (by commit, Dependabot), the CI tool versions (cosign, just, gitleaks, zizmor: by hand). Pins change only through a PR Kevin approves. `bump-pins.yml` (Monday 07:00 UTC, or `gh workflow run bump-pins.yml --ref testing`; `-f dry_run=true` lists what it would open, keep or close and creates nothing) opens ONE PR PER PIN into `testing`, each independent: branch `bump/scx-YYYYMMDD`, `bump/extest-...`, `bump/ghostty-...` (Ghostty and Zig together, Zig never alone) or `bump/builder-...`, cut from current `testing`, one commit, only that pin's lines (different files, so no conflicts): merge any subset in any order, close the rest. At most one open PR per pin (found by the head prefix `bump/<pin>-`), and no force-push is ever used: an open PR that already proposes the same `to` value stays (reruns are idempotent); an open PR with an older value is REPLACED (a new branch `bump/<pin>-YYYYMMDD`, `-2`, `-3` if the name exists, and a new PR are made first, then the old PR is closed with a comment pointing at the new one and its branch deleted); an open PR whose value `testing` already has is closed as stale with a comment; nothing moved means no branch and no PR. Same semantics as octarine-os's bump. A pin whose upstream cannot be read leaves its open PR alone and turns the run red. It uses only `GITHUB_TOKEN` (no PATs, no cross-repo PRs). Needs the repository setting "Allow GitHub Actions to create and approve pull requests". PRs opened with `GITHUB_TOKEN` start no workflow, so `bump-checks.sh` dispatches `test.yml` on `testing` with `ref=<bump commit>` (its run is named `Test of <sha>`, so parallel PRs do not collide; it runs per PR one after another, hence the 60-minute job timeout) and posts check runs named `test` and `secrets` on the bump commit with the real results (`actions: write`, `checks: write`). Scheduled workflows run only from the default branch, so the schedule starts after the first promotion.

Adding pins for a new component of `dx` or `gx`: no pin exists there yet and `bump-pins.yml` and its scripts only know the `src/` kinds (`scx`, `extest`, `ghostty`, `builder`), so they are unaffected. A component `dx/<name>` with an `upstream.env` gets its kind in `bump-run.sh` (the `files=(...)` path of the kind, as `src/${pin}/upstream.env` for the base ones), in the kind list of `bump-weekly.sh` and in the tests; nothing else changes (the branch prefix `bump/<kind>-` stays per pin).

## What octarine-os expects

`octarine-bins:latest` exists, verifies with this repo's `cosign.pub` (the OS build resolves the tag to a digest once and verifies it), and has the layout above, with exactly the components its installer's `required` list names (`scx extest ghostty`), no more. The same holds for `octarine-bins-dx:latest` and `-gx:latest` once the OS installs them (all signed with the same key, the empty layout above until they hold a component). A new or removed component means a coordinated change on both sides (reader first).

**Adding a component to dx or gx:** see `dx/README.md` (the same for gx): a stage copied from `src/Containerfile`, its pin and build script in the image's directory, its name in `components.tsv`, a case in `binaries-layout.sh`, `--allow-empty` removed from the assemble line (so the image can never silently be empty again). The OS reader learns the component first. The scheduler list is `src/scx/schedulers.tsv`; octarine-os generates its registry from the copy inside the image.

## Failure modes and hand fixes

- A component does not build (an upstream download failed, a Fedora package moved, Ghostty/Zig broke): `build` is red, nothing is pushed, `testing` and `latest` stay. Re-run the run if it looks transient; otherwise pin back the component (`upstream.env`; for Ghostty also `zig.env`, together) in a PR. A component that keeps failing is removed in a coordinated change (reader first): its stage, directory, line in `components.tsv`, the layout case in `binaries-layout.sh`, and the OS side.
- `sign` fails after a push: the version tag exists unsigned, `testing` did not move. Re-run `sign`, or push to `testing` again. An unsigned version tag is never promoted (only `testing` and `latest` are).
- Promotion fails ("not signed", "does not exist", "could not be read"): fix the testing build, then re-run the promote run (`gh run rerun`, or `gh workflow run <caller>.yml --ref main`). Exit 4 from a registry or cosign read means a read error, never "absent".
- Promotion fails for one image only: re-dispatch that caller on main (`gh workflow run binaries-dx.yml --ref main`, likewise `binaries.yml`, `binaries-gx.yml`) once its build on `testing` is green. A failing build of dx or gx affects only that image: the three callers are independent, and the base stays promotable.
- The first push of a new package creates it private in GHCR (the images `octarine-bins-dx`, `-gx` and their `-cache` packages): Kevin makes each public and links it to the repo (package settings, "Manage Actions access" with Write for this repository) by hand. The rulesets for `main` must list the required contexts of each caller (`Build the dx binaries image`, `Sign the dx binaries image and move testing`, and the same for gx), added by the hub after a caller's first green run.
- Old testing images accumulate; deleting versions is Kevin's, by hand in the packages UI.

## Scripts (`.github/scripts`)

`retry.sh` (the one retry helper for network calls), `registry-read.sh` (exit 3 absent, 4 read error), `registry-digest.sh`, `registry-settled.sh` (read-back until the tag shows the digest), `cosign-check.sh` (exit 5 not verified, 4 read error), `push-image.sh`, `binaries-layout.sh`, `binaries-inputs.sh` (what rebuilds which image), `binaries-skip.sh`, `binaries-promote.sh`, `upstream-check.sh` and `ghostty-check.sh` (the decisions), `bump-run.sh`, `bump-ghostty.sh`, `bump-weekly.sh`, `bump-checks.sh` (the bump), `sanity.sh`. Retries stay on network calls; "could not read" is never taken for "not there".

## Rules for the agent

- Commit on a feature branch by explicit paths (never `git add -A`), message says why, no Co-Authored-By trailer. Never commit on `testing` or `main`, never force-push, never merge into `main`, never touch rulesets or repository settings. One PR into `testing` per queue, amended (title at most 140 characters; detail in the body). Check `git remote -v` shows `github.com/redcodeworks/octarine-bins` and pass `-R redcodeworks/octarine-bins` to every `gh` command.
- Machine-read files are JSON read with `jq`, never positional TSV where avoidable (the existing `schedulers.tsv` and `components.tsv` are the OS's contract). Tests run the real writer into the real reader; no tests of workflow or README text; keep them slim.
- Local image build for large changes: `PODMAN="podman --root <scratch>/root --runroot <scratch>/run --storage-driver overlay" just build`. Never bulk-remove (`rmi -a`, `system prune`), never touch the real podman storage.
- README: user-facing only (see its sections), American English, "they/them" or first person for Kevin.
