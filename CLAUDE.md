# CLAUDE.md

Guidance for Claude Code in this repository. Read it first; the repo's agent (`bins-project` in the hub) is the only writer here.

## What this repo is

**One sentence: `octarine-bins` is the vanilla binaries image (every octarine-os variant), `octarine-bins-dx` is the dx binaries plus the developer package lists, `octarine-bins-gx` is the gx binaries plus the gaming package lists, and every image carries its own required and optional package lists with the one installer (`/packages`); each is built and signed (this repo's key) on `testing`, promoted to its own `latest` by retag on `main`, and octarine-os pins ONE digest per variant.** The base holds the binaries every variant installs (the sched_ext schedulers `scx`, `extest`, Ghostty with its Zig toolchain), `ghcr.io/redcodeworks/octarine-bins`. `-dx` and `-gx` (skeletons added 2026-11-16) hold the binaries only the dx or the gx image needs (none yet, see "The empty image") and, since the lists moved here from octarine-images on 2026-11-16, the package lists under `/packages` (see "The package lists"). The octarine-os image build reads the `latest` of the images it uses (resolved to a digest and verified) and never looks at this repo's source tree, tags or workflow results. The code was moved here on 2026-11-16 from `binaries/` in octarine-os (now `src/`), together with its CI. The repo keeps the name octarine-bins (a rename is a later, separate decision).

`README.md` is user-facing (what, why, how to use, license, credits, disclaimer); implementation details live here.

## Layout of the repo

- One directory per image: `src/` (the base image, octarine-bins; the name `src` stays because octarine-os pins its digest), `dx/` and `gx/` (each `Containerfile`, `components.tsv`, `packages/` with its package lists, a `README.md`); `src/packages/` holds the base's lists. `installer/` holds the package installer (`install.sh`), ONE copy that all three images copy into `/packages` (named build context `installer`; it is not in `src/lib` so that an installer change does not invalidate the base image's long component stages: only its small assemble stage reruns). Build context of an image is its directory; the SHARED helpers live once, in `src/lib`, and the other images reach them as the named build context `lib` (`just build` passes `--build-context lib=src/lib`; `COPY --from=lib ...`). The pinned builder `src/builder.env` is shared the same way.
- `src/Containerfile`: ONE multi-stage build. A stage per component (`scx`, `extest`, `ghostty`), an `assemble` stage, a final `FROM scratch`. Build context is `src/`. Every component is required: a failing stage fails the build and nothing is pushed (atomic).
- `src/components.tsv` (component names, one per line, comments allowed), `src/builder.env` (the digest-pinned Fedora builder every stage starts from, passed as `--build-arg BUILDER`), `src/<component>/` (`upstream.env` pin, `build.sh`, for scx `schedulers.tsv`, for ghostty `zig.env` and `fetch-zig.sh`), `src/lib/` (`upstream-env.sh` parser, `fetch-source.sh`, `stage.sh`, `assemble.sh`).
- `.github/workflows/`: `test.yml`, `binaries.yml`, `binaries-dx.yml`, `binaries-gx.yml` (the three thin callers: build, sign, promote of one image each), `bump-pins.yml`, `require-testing-branch.yml`. `.github/actions/`: `build-image`, `sign-image`, `promote-image` (the steps the three callers share, ONE copy; composite actions, not a reusable workflow, see below) and `setup-tool` (installs pinned cosign or just). `.github/scripts/`: the helpers (below). `.github/dependabot.yml` bumps the pinned actions (PRs into `testing`).
- `Justfile`: `check` (format check), `build <image> <version> <revision> <dir>`, `layout <image> <dir>`, `test [group]` (`dir` is `src`, `dx` or `gx`); CI calls `build` and `layout` too. `tests/`: grouped by area, one directory per group and the directory tree is the only list (`tests/pipeline/` CI scripts and the bump flow, `tests/registry/` registry, signing and promotion, `tests/image/` layout, package lists and the installer; `tests/conftest.py` and `tests/fakes/` are shared and stay at the top; a test file outside a group, or an empty group, fails `plan_tests.py`). pytest (`just test [group]` runs `uv run --frozen pytest tests/<group>` and the group's `*.sh`, nothing installed globally; the fake `skopeo` and `cosign` programs are real executable Python files in `tests/fakes/`, and `tests/fakes/github_api.py` is a fake GitHub API server (it answers with captured real answers from `tests/fakes/api/*.json`, because githubkit validates every field of a typed response; tests adjust a few fields) (stdlib `http.server` in a thread, started by the `github` fixture in `conftest.py`, reached through `GITHUB_API_URL`) (one docstring each says what it fakes; `tests/conftest.py` puts the directory on PATH, no network; `tests/fakes/bump_run.py` and `bump_checks.py` are the stubs the weekly test copies next to the real `bump_weekly.py`), so no test builds code from strings): `test_retry.py` (the decorator), `test_github.py` (the SDK against the fake API: a 404 raises after one request, a dropped connection is retried), `test_sanity.py`, `test_registry.py`, `test_skip_promote.py` (real git repositories), `test_layout.py` (the real assembler into the layout checker), `test_lint_packages.py`, `test_pins.py` (the real Ghostty writer into the real reader; the weekly decisions with a table of API answers), `test_bump_weekly.py` (real git, stub `gh`). `tests/image/installer.sh` stays bash because it tests `installer/install.sh` (real lists, stub dnf5).
- `cosign.pub` (public, committed) is this repo's OWN key, not shared with octarine-os (one key per repo: a shared key would let a compromised workflow here sign octarine-os images). octarine-os verifies `octarine-bins` with its own copy of this public key; when the key changes, that copy changes first or together. `cosign.key` sits in the repo directory, git-ignored: NEVER read, print, copy, stage or commit it. CI signs with the secret `SIGNING_SECRET` of the environment `signing` (branch policy `main`, `testing`); do not create other secrets or tokens.

## The image layout (the contract with octarine-os)

```
/binaries/            (the image root; octarine-os bind-mounts the image at /binaries)
  COMPONENTS          component names, one per line (written by src/lib/assemble.sh from components.tsv)
  SOURCE, BUILDINFO   the components' records one after the other, each under a [name] heading
  LICENSES/           union of the component license directories
  scx/       bin/<scheduler>..., schedulers.tsv (tab separated, 4 fields: name, bin/name, minimum kernel, description), SOURCE, BUILDINFO, LICENSES/
  extest/    lib/libextest.so (32-bit), lib64/libextest.so, SOURCE, BUILDINFO, LICENSES/
  ghostty/   root/usr/... (the installed tree), FILES (one path under root/ per line), SOURCE, BUILDINFO, LICENSES/
```

**The package lists (every image: `octarine-bins`, `-dx`, `-gx`):** next to `/binaries`'s files the image root holds a directory `packages/`, the contract of the octarine-os installer step (the image root is what octarine-os bind-mounts, so with the mount at `/binaries` the paths are `/binaries/packages/...`). ONE sentence per file: `required-<source>.txt` is what must be installed or the build fails (one strict dnf5 transaction), `optional-<source>.txt` is what is nice to have (installed best effort, what is missing is reported, never a failure), and `<source>` is `fedora` (Fedora's own repositories), `negativo17` (repository `fedora-multimedia`, enabled for that call only) or `copr` (entries `owner/project:name-version-release`, an exact version and release; per entry enable, install, disable). An image carries only the files it needs; the six names are the only ones the installer and the lint accept.

```
packages/install.sh                  the installer (the ONE entrypoint; installer/install.sh here)
packages/required-fedora.txt  required-negativo17.txt  required-copr.txt     strict
packages/optional-fedora.txt  optional-negativo17.txt  optional-copr.txt     best effort
src: required-fedora, optional-fedora, optional-negativo17      (the octarine-os image: the lists build.sh used to hold)
dx:  required-fedora, optional-fedora                           (the developer list, split; plus the VM-hosting and tracing packages of octarine-os's variants/dx/packages/extras.txt)
gx:  required-fedora, required-negativo17, required-copr, optional-fedora   (the gaming lists, split)
```

**The contract of `packages/install.sh`** (needs dnf5 and root, `dnf5-plugins` for copr lists; the consumer calls it ONCE per image, `bash /binaries/packages/install.sh`; it works from a bind mount):

1. Order, fixed: `required-fedora`, `required-negativo17`, `required-copr`, then `optional-fedora`, `optional-negativo17`, `optional-copr`; a missing file is skipped. Required before optional, so a conflicting optional dependency can never replace a required package (dnf5 transactions are atomic).
2. A required file is ONE `dnf5 -y install --setopt=strict=1` transaction: any unavailable package fails the call (exit non-zero, the build fails). A required copr entry that cannot be enabled or installed fails it too (the COPR is disabled again first).
3. An optional file is ONE transaction; on failure it is retried once as a whole (after `RETRY_SLEEP` seconds, default 20, and `dnf5 clean expire-cache`), then package by package. A package that still fails is printed as `OPTIONAL PACKAGE MISSING: <name>` and appended to `$MISSING_FILE`; the call still exits 0. An entry whose `a|b` alternatives all lack is reported the same way (in a required file it fails). An optional copr entry that cannot be enabled or installed is reported the same way.
3a. Every list is read into an array before anything runs (`mapfile`), never inside a `while read` loop that runs dnf5: dnf5 reads stdin and silently ended the loop at the first `a|b` line (found 2026-11-16: dx installed 101 of 112 entries). The installer also checks the counts: entries read = entries in the file, and installed + excluded + missing = entries read, else it fails the build. `tests/installer.sh` has a stub dnf5 that reads stdin like the real one.
4. `MISSING_FILE=<path>`: appended to, created if absent, never truncated (the consumer empties it once, so the base's call and dx's call add up); unset, the report is only printed. The names are one per line, the format octarine-os's smoke test reads (`/usr/share/octarine-os/optional-packages-missing`).
5. `EXCLUDE="a b"` drops entries (a name, an alternative, an `@group`); `ENABLE_REPO="id ..."` enables more repositories for every call; `NO_CLEANUP=1` skips the dnf cache cleanup at the end (otherwise `dnf5 clean all` and the build residue are removed); `PACKAGES_DIR` and `RETRY_SLEEP` are for tests. Log groups (`::group::Packages: <tier> <source>`) are printed for the GitHub Actions log.
6. Not done here, because it is the OS's: the check that niri and noctalia (optional, but a session without them is broken) are not in the missing file, the vendor check of the required packages, `validate-repos.sh`, and installing `dnf5-plugins`. The old `install-copr.sh` is gone (one entrypoint); the old per-list calls and `ENABLE_REPO=fedora-multimedia` for negativo17 are the installer's job now.

The binaries contract is unchanged: `/COMPONENTS` is the list of binary components, `packages/` is not a component and is not named in it; an image with `packages/` and an empty `/COMPONENTS` is valid. A reader that checks the top level of the image must allow `packages`. Adding a list file or an installer option is compatible; renaming or removing a file under `packages/` is a layout change (reader first, below). The base image gained `packages/` on 2026-11-16 (the OS reader that does not look at it is unaffected); octarine-os pins the base by digest, so nothing changes there until it bumps and starts calling the entrypoint.

List policy (Kevin, 2026-11-16): Fedora's own repositories (`*-fedora.txt`), negativo17 (`*-negativo17.txt`), COPR only through `*-copr.txt` with an exact version and release; no RPM Fusion. A package that is not Fedora's is optional unless the image cannot be what it is without it (gx: Steam and Sunshine are required, as they were strict before). `required-fedora.txt` of the base holds only Fedora packages (the OS smoke test checks the RPM vendor). List syntax: one entry per line, `#` comments; `name`, `name.arch`, `@group-id` or `a|b` alternatives (first existing one wins, none existing fails a required file; dx uses it for names that differ between Fedora releases); every `name.i686` needs `name.x86_64` listed in the same file (a bare name next to an i686 one installs only i686 on a host); no entry twice, in one list or across the image's lists; `python3 -I .github/scripts/lint_packages.py <the image's lists>` enforces all of it and `tests/test_lint_packages.py::test_the_real_lists_pass[src|dx|gx]` runs it on each image's real lists (`tests/installer.sh` runs the installer on them with a stub dnf5). A list change rebuilds only that image (`<dir>/packages/` is content of its image; `installer/` rebuilds all three images) and the promotion guard compares the same content.

**The empty image (`octarine-bins-dx`, `-gx`, until they get a component):** `/COMPONENTS` is EMPTY (zero bytes), there is no `/binaries/<name>/` directory, `BUILDINFO` and `SOURCE` exist and are empty, `LICENSES/` exists and is empty, and the labels are set. Zero components means nothing to install. `src/lib/assemble.sh --allow-empty` writes it (the base never passes the flag: an empty list there is an error), and `binaries_layout.py` (`allow_empty`) accepts it (`just layout` passes the flag for `dx` and `gx` only; every image gets `--packages` naming the files that must be in `packages/`; the base must still hold scx, extest and ghostty, and a base missing one fails). The octarine-os reader today treats an empty `COMPONENTS` as "not an assembled binaries image" (`test -s`) and has a fixed `required` list, so the dx/gx reader must accept zero components before the OS installs these images; it is a new reader step in octarine-os, not a layout change of the base.

**Build on content, stamp every build (2026-11-17).** A push to `testing` builds an image only if its CONTENT changed since the commit its `testing` image was built from. Every build is stamped with `org.opencontainers.image.version` (`<UTC date>-<short sha>`), `.revision` (the full commit it was built from) and `.created` (the build arguments `just build <image> <version> <revision> <dir>` set them; `built=` in `SOURCE` also carries the time), so the `revision` label names that commit. Skip: the content inputs at the revision label's commit equal those at `HEAD` and `testing` verifies with `cosign.pub`. Promote: retag the tested, signed `testing` digest to `latest` after checking that its revision's content equals `main`'s content. So a new digest always means a build ran for a content change (a build that is not skipped is never byte-identical: the labels and `built=` carry the time), and octarine-os's weekly bump PR follows content changes only. Content is defined ONCE, `ci.inputs(<dir>)` in `.github/scripts/ci.py`, derived from each Containerfile's `COPY` lines and used by the skip AND the promotion guard (`ci.content_id`: sha256 of `git ls-tree -r <commit> -- <inputs>` without `*.md` files): base `octarine-bins`: all of `src/` (Containerfile, `components.tsv`, `builder.env`, `lib/`, the components, `packages/`) and `installer/`; `dx` and `gx`: `<dir>/Containerfile`, `<dir>/components.tsv`, `<dir>/packages/`, `src/lib/assemble.sh`, `src/builder.env` and `installer/`. Not content: the Justfile, `.github/**` (workflows, actions, scripts), tests, READMEs and other docs. **Tooling-only changes build NOTHING**; they are validated by a manual dispatch (`gh workflow run <caller>.yml --ref testing`, which always builds) or by the next content change. Because the labels vary, never compare digests of two builds of the same content: they differ by design. The registry tags are `<UTC date>-<short sha>` (immutable: `push_image.py` keeps an existing tag and its digest instead of overwriting it, which only happens when the same commit is built twice on one day), `testing` and `latest`; the older `inputs-<hash>` tags in the registry (from #29, 2026-11-17) are unused.

**A layout change goes reader-first:** octarine-os (`build_files/install-binaries.sh`, `gen-schedulers.sh`, the smoke tests) first accepts BOTH the old and the new layout, then this repo writes the new one, then the OS drops the old one. Say so under `Needs from hub:` whenever the layout would change. `.github/scripts/binaries_layout.py` (run on every built image by `just layout`) is this repo's copy of what the reader needs; `tests/test_layout.py` runs the real assembler into it.

## Branches, CI and promotion (GitLab Flow)

1. A push to a feature branch (`feat/`, `fix/`, `chore/`) runs `test.yml`: job `plan-tests` (lists the groups), job `sanity` (`sanity.py`: `bash -n` on every shell script, a compile of every Python file, workflow parse; then `just check`), one job `tests (<group>)` per group (`just test <group>`), job `test` (the aggregate, `if: always()`, succeeds only when all of those did; the one required name, which `bump_checks.py` reads from the dispatched run) and job `secrets` (gitleaks over the full history). The same workflow has job `zizmor` (workflow audit with the pinned zizmor, `.github/zizmor.yml` config; runs on every push and weekly on Wednesdays 06:00 UTC, which is the only job of the scheduled run; skipped on a dispatch; not required, `test` does not depend on it). Open a PR into `testing`. Required checks (ruleset, set by the hub): `test` and `secrets`.
2. A push to `testing` runs the three callers `binaries.yml`, `binaries-dx.yml` and `binaries-gx.yml`, each with its own concurrency group, so each image has its own queue. Per image: `build` (`.github/actions/build-image`: first `binaries_skip.py`, see "Skipping a build"; then `just build`: the whole multi-stage build with a registry layer cache (below); `just layout`; `push_image.py` pushes the immutable tag `<date>-<sha>` and prints the digest), then `sign` (`environment: signing`, `.github/actions/sign-image`: `cosign sign` that digest with the old bundle format, verify with `cosign.pub`, and only THEN `skopeo copy --preserve-digests` to `:testing`, read it back with `registry.settled`, verify again). So `testing` never points at an unsigned image. Why callers and composite actions rather than one reusable workflow (as octarine-os's dx image does): the job names are required checks (`Build the binaries image`, `Sign the binaries image and move testing`, and the same with `dx ` and `gx `), and a job of a reusable workflow is reported as `<caller job> / <called job>`; the signing environment secret also does not reach a job inside a reusable workflow (observed 2026-11-16). Composite actions run inside the caller's own job, so the names and `environment: signing` stay and the steps exist once.
3. A promotion PR from `testing` into `main` (only from `testing`: `require-testing-branch.yml`; Kevin merges it) makes the push to `main` run each caller's `promote` job (`.github/actions/promote-image`): `binaries_promote.py` retags the TESTED, signed `:testing` digest of that image to its `:latest` (no rebuild). It fails loudly, changing nothing, unless `testing` exists, verifies with `cosign.pub` and IS the build of these inputs (guard below); when `latest` already is that digest it does nothing; afterwards it reads the tag back and verifies through `:latest`. Nothing else moves `latest`.
4. A dispatch from any other ref builds for validation and publishes nothing. By hand, per image: `gh workflow run <caller>.yml --ref testing` rebuilds, `--ref main` promotes.
5. Builds are not path filtered: every push to `testing` and `main` runs all three callers (`main` only promotes). Runs of one ref and image queue, none is cancelled (`cancel-in-progress: false`), so two runs never move `testing` out of order. A superseded older `testing` run may be cancelled by hand; never a `main` or a signing run, never the tip.

Cost of an unchanged push to `testing` (skip path): 3 workflow runs, 6 jobs (`build` and `sign` each), roughly 30 to 60 s per `build` (checkout, login, cosign install, the registry reads) and a few seconds per `sign`, in parallel; on `main` 3 `promote` runs of about a minute that find `latest` already the tested digest.

Promotion guard: `binaries_promote.py <image> <dir>` also fails, changing nothing, unless `testing` IS the build of exactly what is promoted: the content (`ci.content_id`, above) at the commit of `testing`'s `revision` label must equal the content of `HEAD` of the main checkout (the promotion PR's merge commit; its content equals the testing tip's when main has nothing testing lacks, which the ruleset ensures; the first promotion works the same). Tooling and docs are no content, so they never make the image stale. A mismatch means the build on testing is running, failed, or testing moved on. A cosign read error is printed as such, not as 'not signed'. Hand fix: wait for the tip's build on `testing` to be green, then `gh run rerun` the promote run (or `gh workflow run <caller>.yml --ref main`).

## Speed: parallel stages, layer cache, skipped builds (2026-11-16)

- **Parallel stages:** `just build` passes `--jobs 3`, so the scx, extest and ghostty stages build at the same time (they share nothing but the builder). The runner has about 4 cores, so only part of the gain shows.
- **Layer cache:** `--layers --cache-from ghcr.io/redcodeworks/<image>-cache` on every build, plus `--cache-to` the same package only on `testing` (`main` builds nothing). One cache package per image (`octarine-bins-cache`, `octarine-bins-dx-cache`, `octarine-bins-gx-cache`): buildah keeps its layers as tags of ONE repository, so tags cannot keep three caches apart. The cache is a separate package, never the image's tags; it needs `packages: write` (the build job has it; GITHUB_TOKEN, nothing else). Invalidation: a new `builder.env` digest changes the `FROM` of every stage, so everything rebuilds; a Ghostty pin change rebuilds only the ghostty stage (the earlier layers, dnf included, hit); an scx pin only scx; a change to `src/lib` rebuilds all stages (`COPY lib`); a change to a stage's `COPY` directory rebuilds that stage from the `COPY` on. The dnf layers are frozen until the builder pin or the text of the instruction changes: Fedora package updates reach the binaries only with a builder bump or an edit of that line (a reproducibility gain, accepted). The first run, or a package that does not exist yet, is a cold build, not a failure. The cache only saves time: what is published is decided by the layout check before the push and by the signature. If the cache cannot be read for another reason and podman fails, the build fails plainly: re-run it, or run the workflow once with the cache flags removed.
- **Skipping a build** (`binaries_skip.py`, push to `testing` only; a dispatch always builds): when the content of this commit equals the content at the `revision` label's commit of `testing` and that image verifies with `cosign.pub` ("Build on content"), the `build` step is skipped and the `sign` job does nothing. Both jobs still run and succeed (the ruleset requires their names `Build the binaries image` and `Sign the binaries image and move testing`; never use `paths:` filters). So a change to `src/lib/assemble.sh` or `installer/` rebuilds all three images, to `src/builder.env` or the base's own `src/` files (the other `src/lib` helpers included) the base (and for the builder pin also dx and gx), to `dx/`'s Containerfile, `components.tsv` or lists only dx, likewise gx; the Justfile, workflows, actions, scripts, tests and READMEs rebuild nothing. No testing image, a testing image without a valid revision label, an unfetchable revision, other content, or an image that does not verify (for example signed with an old key) means build. A registry or cosign READ error fails the run instead of guessing. The first run builds (no testing image). A rebuild by hand: `gh workflow run <caller>.yml --ref testing`.

## Pin policy

Pins: scx and extest (`src/<c>/upstream.env`: tag and/or commit), Ghostty (`src/ghostty/upstream.env`) with Zig (`src/ghostty/zig.env`: Zig changes ONLY together with a Ghostty pin, its minor follows from the tag), the Fedora builder digest (`src/builder.env`, bumped once the digest has been the tag's value for 7 days), the GitHub Actions (by commit, Dependabot), the CI tool versions (cosign, just, gitleaks, zizmor: by hand). Pins change only through a PR Kevin approves. `bump-pins.yml` (Monday 07:00 UTC, or `gh workflow run bump-pins.yml --ref testing`; `-f dry_run=true` lists what it would open, keep or close and creates nothing) opens ONE PR PER PIN into `testing`, each independent: branch `bump/scx-YYYYMMDD`, `bump/extest-...`, `bump/ghostty-...` (Ghostty and Zig together, Zig never alone) or `bump/builder-...`, or `bump/python-deps-...` (`uv lock --upgrade`: newer locked versions of the CI scripts' own dependencies, only `uv.lock` changes; the `pyproject.toml` ranges and the Python version stay), cut from current `testing`, one commit, only that pin's lines (different files, so no conflicts): merge any subset in any order, close the rest. At most one open PR per pin (found by the head prefix `bump/<pin>-`), and no force-push is ever used: an open PR that already proposes the same `to` value stays (reruns are idempotent); an open PR with an older value is REPLACED (a new branch `bump/<pin>-YYYYMMDD`, `-2`, `-3` if the name exists, and a new PR are made first, then the old PR is closed with a comment pointing at the new one and its branch deleted); an open PR whose value `testing` already has is closed as stale with a comment; nothing moved means no branch and no PR. Same semantics as octarine-os's bump. A pin whose upstream cannot be read leaves its open PR alone and turns the run red. It uses only `GITHUB_TOKEN` (no PATs, no cross-repo PRs). Needs the repository setting "Allow GitHub Actions to create and approve pull requests". PRs opened with `GITHUB_TOKEN` start no workflow, so `bump_checks.py` dispatches `test.yml` on `testing` with `ref=<bump commit>` (its run is named `Test of <sha>`, so parallel PRs do not collide; each pin's job waits for its own, hence the 30-minute job timeout) and posts check runs named `test` and `secrets` on the bump commit with the real results (`actions: write`, `checks: write`). The workflow is a MATRIX, one job per pin (`Bump <pin>`, `fail-fast: false`; the matrix in `bump-pins.yml` is the only list of pins and passes its pin to `bump_weekly.py` as `BUMP_PINS`, which is required, so a hand run names the pins: `BUMP_PINS=scx python -I .github/scripts/bump_weekly.py`); adding a kind adds one matrix entry. The jobs do not collide: branches are per pin, test runs and check runs are keyed by the bump commit, and `python-deps` (`uv.lock`) and `python` (`.python-version`) touch different files. Each job checks out `testing` and sets up uv and Python itself (cache on; no signing key there), and one failing pin turns only its own job red. Scheduled workflows run only from the default branch, so the schedule starts after the first promotion.

Adding pins for a new component of `dx` or `gx`: no pin exists there yet and `bump-pins.yml` and its scripts only know the `src/` kinds (`scx`, `extest`, `ghostty`, `builder`), so they are unaffected. A component `dx/<name>` with an `upstream.env` gets its kind in `bump_run.py` (the `files` path of the kind, as `src/<pin>/upstream.env` for the base ones), in the kind list of `bump_weekly.py` and in the tests; nothing else changes (the branch prefix `bump/<kind>-` stays per pin).

## What octarine-os expects

`octarine-bins:latest` exists, verifies with this repo's `cosign.pub` (the OS build resolves the tag to a digest once and verifies it), and has the layout above, with exactly the components its installer's `required` list names (`scx extest ghostty`), no more. The same holds for `octarine-bins-dx:latest` and `-gx:latest` once the OS installs them (all signed with the same key; the empty binaries layout above until they hold a component, plus the `packages/` directory of "The package lists", which octarine-os's installer step reads: one digest pinned per variant). A new or removed component means a coordinated change on both sides (reader first).

**Adding a component to dx or gx:** see `dx/README.md` (the same for gx): a stage copied from `src/Containerfile`, its pin and build script in the image's directory, its name in `components.tsv`, a case in `binaries_layout.py`, `--allow-empty` removed from the assemble line (so the image can never silently be empty again). The OS reader learns the component first. The scheduler list is `src/scx/schedulers.tsv`; octarine-os generates its registry from the copy inside the image.

## Failure modes and hand fixes

- A component does not build (an upstream download failed, a Fedora package moved, Ghostty/Zig broke): `build` is red, nothing is pushed, `testing` and `latest` stay. Re-run the run if it looks transient; otherwise pin back the component (`upstream.env`; for Ghostty also `zig.env`, together) in a PR. A component that keeps failing is removed in a coordinated change (reader first): its stage, directory, line in `components.tsv`, the layout case in `binaries_layout.py`, and the OS side.
- `sign` fails after a push: the `<date>-<sha>` tag exists unsigned, `testing` did not move. Re-run `sign`, or push to `testing` again. An unsigned `<date>-<sha>` tag is never promoted (only `testing` and `latest` are).
- Promotion fails ("not signed", "does not exist", "could not be read"): fix the testing build, then re-run the promote run (`gh run rerun`, or `gh workflow run <caller>.yml --ref main`). Exit 4 from a registry or cosign read means a read error, never "absent".
- Promotion fails for one image only: re-dispatch that caller on main (`gh workflow run binaries-dx.yml --ref main`, likewise `binaries.yml`, `binaries-gx.yml`) once its build on `testing` is green. A failing build of dx or gx affects only that image: the three callers are independent, and the base stays promotable.
- The first push of a new package creates it private in GHCR (the images `octarine-bins-dx`, `-gx` and their `-cache` packages): Kevin makes each public and links it to the repo (package settings, "Manage Actions access" with Write for this repository) by hand. The rulesets for `main` must list the required contexts of each caller (`Build the dx binaries image`, `Sign the dx binaries image and move testing`, and the same for gx), added by the hub after a caller's first green run.
- Old testing images accumulate; deleting versions is Kevin's, by hand in the packages UI.

## Scripts (`.github/scripts`)

**Python for the CI side** (the installer and the Containerfile steps stay bash). Dependencies are declared in `pyproject.toml` (`githubkit`, which brings `httpx` and `pydantic`; `packaging`; `pyyaml`; `pytest` in the `dev` group) and pinned with hashes in the committed `uv.lock`; the Python itself is pinned EXACTLY by `.python-version` (`3.14.10`, a uv-managed interpreter; `requires-python >=3.14` is only the floor the lock is valid for). The runner image's system Python is NOT used: the composite action sets `UV_PYTHON_PREFERENCE=only-managed`, so uv downloads the pinned interpreter instead of silently taking `/usr/bin/python3.14`, whose patch version floats with the runner image; uv checks the sha256 embedded in its own pinned release metadata after the download. The weekly bump has a `python` kind that proposes the newest patch release of that minor which the pinned uv can install (a newer one appears after a uv bump, which is by hand). Every script runs as `uv run --frozen --no-dev python -I .github/scripts/<name>.py`: `--frozen` means nothing is resolved at run time (the lock decides), and `uv run` creates the venv and installs it, so no separate sync step is needed. `-I` keeps the script's directory off `sys.path`, so each script starts with two lines that add it back. In CI the composite action `.github/actions/setup-ci-python` installs uv (`astral-sh/setup-uv`, SHA-pinned) with its cache ON, keyed on `uv.lock` and `.python-version`, and `cache-python`, so the managed Python is saved on the first run and restored later (a Python or lock bump changes the key and invalidates it). The sign job holds the signing key and restores no cache of any kind (`cache: false` on both setup actions): it installs the uv packages from the frozen lock, downloads the pinned managed Python and installs cosign fresh on every run, and those install steps verify what they download (uv checks the sha256 of its managed Python; the pinned `sigstore/cosign-installer` verifies cosign against a checksum embedded in the action). The standard library is used for `argparse` (every script that reads arguments, `--help` shows the first sentence of its docstring), `logging` (`ci.log`, one handler that writes the `::error::` and `::warning::` annotations; no scattered prints) and `subprocess` (argument lists, never a shell); `packaging.version.Version` orders versions; `pydantic` validates what untrusted JSON is read into (`pins.Pin` and `pins.Decision` dataclasses, the Zig index and the release JSON as models); `httpx` downloads what is not the GitHub API (the Zig index, with a timeout and `follow_redirects`). One sentence at the top of each file says what it does. **Shared code lives in `ci.py`** (THE helpers file: `log`, `@retry`, `github()`, `retry_decision`, `git`, `group`, `version`, `emit`, `inputs(dir)`, `arg_parser`) **and `registry.py`** (every skopeo, cosign and podman call). **The rules: the GitHub API is used through the githubkit SDK directly (`gh = ci.github()`, then `gh.rest.<group>.<operation>(...)`, typed responses, `gh.rest.paginate(...)` as a lazy iterator; keep the `gh` variable, `gh.rest` only holds a weak reference to it); its `auto_retry` handles rate limits and 5xx, `ci.retry_decision` adds transport errors through the SDK's own retry-decision API, and its exceptions are not wrapped: an error ends the script with the SDK's traceback, and `RequestFailed` is caught only where a decision depends on the status (a 404 means "no release", or "the fork does not have the commit"). Every external command and every other network call goes through `@ci.retry`; nowhere else is there a retry loop.** `@retry(on=(...), attempts=, delay=, backoff=)` retries only the exception types in `on` (transient failures), waits `delay` x try number seconds (RETRY_TRIES 3 and RETRY_DELAY 5 by default, shortened through the environment in tests), never retries any other exception, and re-raises the last error with ` (failed N attempts)` in its message. A definitive answer is a typed exception that is NOT in `on`, so it surfaces at once: `registry.Absent` (skopeo: the tag does not exist), `registry.NotVerified` (cosign: no valid signature), a githubkit `RequestFailed` (an error status); `registry.ReadError`, `ci.NetworkError` and `ci.ServerError` are the transient ones. So "could not read" is never taken for "not there". The API server comes from `GITHUB_API_URL` and the token from `GITHUB_TOKEN` (workflows that use the API set it from `github.token`), so the tests can point the scripts at a local fake. Scripts (each has a `main`): `push_image.py`, `sign_image.py` (sign, verify, copy to `testing`, read back, verify), `binaries_skip.py`, `binaries_promote.py`, `binaries_layout.py <image> <dir>` (exports the image with podman and checks it; `check()` is what the tests call), `lint_packages.py` (the list rules, run per image), `upstream_check.py` and `ghostty_check.py` (the decisions; each also has `check()`, which `bump_run.py` calls), `bump_run.py` (one pin), `bump_weekly.py` (all pins), `bump_checks.py` (its sleep is a poll for the dispatched run to appear, not a retry), `sanity.py`; `pins.py` holds the pin files (the Python twin of `src/lib/upstream-env.sh`, which the build scripts inside the container still use). **The original shell scripts and tests are kept in `.archive/shell-ci/`** (see its README: a revert is a file move); nothing runs or checks them and they are not an image input.

## Rules for the agent

- Commit on a feature branch by explicit paths (never `git add -A`), message says why, no Co-Authored-By trailer. Never commit on `testing` or `main`, never force-push, never merge into `main`, never touch rulesets or repository settings. One PR into `testing` per queue, amended (title at most 140 characters; detail in the body). Check `git remote -v` shows `github.com/redcodeworks/octarine-bins` and pass `-R redcodeworks/octarine-bins` to every `gh` command.
- Machine-read files are JSON read with the `json` module, never positional TSV where avoidable (the existing `schedulers.tsv` and `components.tsv` are the OS's contract). Tests run the real writer into the real reader; no tests of workflow or README text; keep them slim.
- Local image build for large changes: `PODMAN="podman --root <scratch>/root --runroot <scratch>/run --storage-driver overlay" just build`. Never bulk-remove (`rmi -a`, `system prune`), never touch the real podman storage.
- README: user-facing only (see its sections), American English, "they/them" or first person for Kevin.
